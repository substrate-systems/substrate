## Context

Cloud uses the existing users, browser sessions, OAuth transactions/grants/tokens and plain cell ownership. `reviewer-access.ts` already supplies Argon2id, random opaque credentials, bounded expiry and throttling. Existing credentials carry lineage through sessions and OAuth, but Hosted issuance/redemption requires old cells/cohorts/artifacts, and Cloud redemption explicitly refuses it. The Cloud gateway token lookup intentionally omits reviewer joins.

## Goals / Non-Goals

Provide independently usable review login to a dedicated sample Cloud tenant. Preserve normal email-link login, OAuth client admission, fixed cell principal and read/write scopes. Never enable old credentials under Cloud, create a cell through login, inspect another vault, or add a new authentication service. Reuse the already drawn reviewer disclosure/form; no new screen or layout.

## Decisions

1. Add `cloud_provider_review` as an explicit immutable credential kind in the existing credential table. Its candidate/assignment/artifact fields remain NULL. An additive migration updates both kind and complete-lineage constraints and adds a Cloud-only active-provider uniqueness index. Existing kinds, rows and indexes retain their semantics. A distinct kind prevents old credentials from becoming Cloud credentials; a second unrelated credential service would duplicate hashing and lifecycle.
2. Cloud operator issuance requires an existing, non-deleted reviewer-purpose tenant owning a non-deleted running Cloud cell, unblocked owner and a complimentary active entitlement with no payment-provider customer/subscription/transaction references. Issuance never marks an ordinary tenant as a reviewer or admits/provisions a tenant. Both existing Cloud invitation redemption paths must propagate the invitation's immutable reviewer-purpose field on initial tenant creation and require exact purpose equality before reusing a tenant; the current omission means reviewer invites otherwise create ordinary tenants. The operator must create/select a dedicated sample tenant through normal admission. Reuse the bounded expiry validation (maximum90days); initial review access is30days. Status is value-free. Plain credentials are returned once through the operator API and entered only in secure reviewer fields.
3. Add a small Cloud store beside `cloud-oauth.ts`; reuse existing hashing/rate-limit/session-cookie primitives. Cloud redemption requires both Cloud and reviewer flags, strict same-origin/CSRF continuity and a live Cloud-resource transaction. Authenticate only the new kind. Bind the exact credential to the transaction and browser session atomically; reject a transaction bound to another credential. Provider must match the already admitted client's platform. Client admission stays ordinary Cloud pinned/CIMD admission, with no cohort/artifact exception.
4. Reuse existing shared grant/code/token issuance and refresh only after real-Postgres tests show they preserve reviewer lineage, provider and expiry. Cloud access lookup additionally validates matching credential/tenant/user/provider/kind and live expiry for a reviewer lineage; ordinary NULL lineages remain unchanged. No Hosted kind is accepted for a Cloud-resource session/grant/token. Codes, browser sessions, refresh families and access tokens never outlive the credential.
5. Rotation and revocation serialize with redemption/issuance, revoke the selected credential's browser sessions, unconsumed authorization transactions/codes, grants, refresh families/tokens and access tokens in one transaction. Query by credential ID, never all tenant grants: the two providers and unrelated sessions must remain independent. Shared code-exchange/refresh already take a tenant lock in a separate statement before mutation snapshots; use that same tenant-first lock for every new Cloud writer. When rotating between tenants, lock affected tenant rows in stable UUID order before credential/session/transaction/grant rows. Make shared consent explicitly lock the tenant before its session, so revocation's tenant-then-session order cannot deadlock. Credential selection before the lock is only routing; revalidate authority after acquiring the lock. Barrier tests race revocation with first-ever grant creation, redemption, code exchange and refresh. Refresh must compare family/grant/refresh credential IDs even when candidate lineage is NULL. Do not reuse browser-session rotation unchanged: it must retain reviewer identity and its expiry cap. Reuse/extract existing credential-lineage revocation where safe; account deletion keeps tenant-wide consent revocation/purge behavior.
6. Keep admin and redemption routes' Hosted behavior unchanged when Cloud is off. Under Cloud, select only Cloud-specific operations. The existing authorization page shows its reviewer disclosure only when the applicable path is enabled and a current OAuth continuation exists. A browser session offers Connect only when its nullable reviewer credential matches the pending continuation; a reviewer session from a previous connection must offer fresh reviewer sign-in. This presentation check never replaces the atomic consent authorization checks. Reconcile D2's pending design/spec language to preserve refusal specifically of Hosted reviewer credentials.
7. Preserve credential kind/identity in the resolved browser-session context. Cloud reviewer sessions are denied checkout initiation/resumption and customer-portal creation before any billing side effect, even if a payment reference is attached after issuance. Ordinary and Hosted flag-off sessions retain their behavior. Complementary eligibility is rechecked at reviewer redemption/consent/mint/refresh/MCP access; payment-bearing sample accounts cease to provide reviewer authority. A private reviewer account is not an owner-billing credential.

## Risks / Trade-offs

Issuance additionally checks observed running/ready health so review access starts on a usable cell. Lifetime authority checks the non-deleted cell's desired running state, not volatile observed health: runtime unavailability remains a routing concern, as for ordinary Cloud access, rather than revoking otherwise valid reviewer identity.

- A sample tenant accidentally owning private content → issuance requires explicit reviewer-purpose marking established by admission, never flips it on an existing owner tenant.
- A revoked/expired credential surviving through a token → real-Postgres full OAuth flow and gateway access checks, expiry caps and atomic lineage revocation, including concurrent operations.
- Cross-resource/provider confusion → explicit kind/resource/platform checks at redemption, authorization, mint/refresh and access; old credentials remain refused.
- A backend-only test hiding a broken review login → independent clean-browser OAuth sign-in on the delivered site, followed by sample MCP bootstrap/capture/readback.
- Shared credential helpers expanding alpha authority → Cloud functions contain no cohort, candidate, release or Hosted-cell dependency; regression suite preserves flag-off behavior.

## Migration Plan

Run the additive migration through the repository's ordinary migration-before-web-deploy process after independent security approval and green CI. Apply the central gateway column-grant script and verify ordinary and reviewer token lookup as `exomem_gateway`, including denial of credential hashes/digests, before deploying the new gateway. Deploy the verified web build and publish/pin a new gateway image: the gateway bundles `findCloudOAuthAccessToken`, so its reviewer lifetime checks must ship too. Existing Cloud cells need no new image for this auth change. Enable the existing reviewer feature flag on both web and gateway only after their verified binaries, migration and grants are deployed and a dedicated sample account is ready. Test the actual provider sign-in without owner cookies/inbox; store credentials through secret custody and secure portal fields, never Git/demo/chat. Roll back by disabling reviewer access on both processes and revoking Cloud reviewer lineage; retain additive schema and do not roll back into a binary that accepts the new kind as Hosted authority. Normal Cloud users continue through email links.
